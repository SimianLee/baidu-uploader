# 百度网盘分批上传工具（非会员友好版）

Win10 命令行 + 网页可视化面板：把本地目录的文件**分批**上传到百度网盘指定目录，专门针对非会员的上传数量限制做了批处理；超过大小上限的文件自动跳过防失败；上传成功的文件可**手动确认**后移动到"已完成"目录或送入回收站。

## 目录结构

```

├── README.md              # 本说明
├── requirements.txt       # 依赖（requests / send2trash）

├── config.example.json    # 配置模板（复制成 config.json 后填写）
├── upload_baidu.py        # 上传主程序（命令行入口）

├── verify_remote.py       # 上传完成后核对网盘 vs 本地记录（只读）
├── pan_tools.py           # 网盘整理引擎：批量改名/归档/删除/空目录/计划校验（纯标准库）
```

## 一、前置准备（一次性，约 10 分钟）

本工具走**百度网盘开放平台**官方 API（`pan.baidu.com/union`），需要免费注册个应用拿密钥：

1. 打开 https://pan.baidu.com/union/main/all ，用你的百度账号登录，申请成为**个人开发者**（免费）。
2. 控制台里「创建应用」：
   - 应用类型选 **个人应用**（个人自用足够）
   - 记下 **AppKey** 和 **SecretKey**
3. 把 `config.example.json` 复制一份改名为 `config.json`，填入这两个值。

> 个人应用有官方免费的 API 调用配额，日常备份文件完全够用。若某天提示配额/频控（errno=31034），把 `batch_pause_sec` 调大即可。

## 三、使用

### 1. 首次登录（二选一）

**方式 A：授权码模式（推荐，不限时）**

浏览器打开下面网址（AppKey 替换成自己的），登录并确认授权，页面会显示一串授权码：

```
https://openapi.baidu.com/oauth/2.0/authorize?response_type=code&client_id=你的AppKey&redirect_uri=oob&scope=basic,netdisk
```

```bat
python upload_baidu.py --login-code
```

按提示粘贴授权码即可。授权码约 10 分钟有效、只能用一次。

**方式 B：设备码扫码（限时 5 分钟）**

```bat
python upload_baidu.py --login
```

按提示打开 https://openapi.baidu.com/device ，输入终端显示的验证码，手机扫码确认。超时或失败就换方式 A。

两种方式 Token 都存在 `token.json`，之后自动续期，无需重复登录。

### 2. 先干跑看看计划（不上传，强烈建议第一次先跑这个）

```bat
python upload_baidu.py --dry-run
```

输出：哪些文件上传、哪些因超大被跳过、分成几批、每批多少个。

### 3. 正式上传

```bat
python upload_baidu.py
```

### 4. 其他参数

| 参数 | 作用 |
|---|---|
| `--batch-size 30` | 临时改每批文件数（默认取配置里的 500） |
| `--limit 5` | 本次只传前 5 个（小规模试水） |
| `--layout flat` | 临时改网盘目录布局（mirror/flat/by_category/by_ext，见下表） |
| `--yes` | 跳过手动确认（`after_upload` 为 ask 时视作保留原处） |
| `--config xx.json` | 指定别的配置文件 |

## 四、配置项说明（config.json）

| 配置项 | 推荐值 | 说明 |
|---|---|---|
| `app_key` / `secret_key` | - | 开放平台应用密钥，必填 |
| `local_dir` | - | 本地待上传目录，必填 |
| `remote_dir` | `/apps/baidu_uploader` | 网盘目标目录（不存在会自动创建，可改成如 `/我的备份`） |
| `batch_size` | 500 | **每批文件数**——非会员限制的核心对策，海量小文件用 500；被限制就调小到 50~100 |
| `workers` | 8 | **并发路数**——一批之内同时上传几个文件，这是提速的关键，见下方实测表 |
| `batch_pause_sec` | 5 | 批与批之间暂停秒数，模拟"手动分次上传" |
| `file_interval_sec` | 0 | 单个文件间隔；并发模式下已无必要，保持 0 即可（被限流时再调到 0.2~0.5） |
| `max_file_size_mb` | 4096 | **大文件上限**，超过的直接跳过并列出清单，防止传一半失败浪费时间 |
| `chunk_size_mb` | 4 | 分片大小，保持 4（官方标准）别改 |
| `recursive` | true | 是否递归子目录（远程保持同样目录结构） |
| `upload_layout` | mirror | **网盘目录布局**：`mirror` 按本地目录结构原样长一份 / `flat` 全部平铺进目标目录（同名自动加 (1)(2) 序号） / `by_category` 按文件大类分目录（视频/文档/图片…，与网盘整理功能同一套分类口径） / `by_ext` 按扩展名分目录（mp4/pdf/txt…）。命令行可用 `--layout` 临时覆盖 |
| `done_dir` | 空 | 上传成功后文件的归档目录；留空则自动取「本地目录同级/已上传」 |
| `after_upload` | keep | 成功后处理：`ask` 每次手动确认（仅命令行）/ `move` 移动 / `trash` 进回收站 / `keep` 不动 |
| `exclude_patterns` | 常见垃圾文件 | 通配符排除规则 |

> `batch_size: 500 / workers: 8 / batch_pause_sec: 5` 这组参数是在 9.9 万个小文件、21GB 的真实场景下实测调优出来的，一般无需修改。

### 并发路数实测（同一批真实小文件，24 个样本）

| 并发路数 | 单文件均耗时 | 吞吐 | 提速 |
|---|---|---|---|
| 1（串行） | 3.95 s | 93 KB/s | 基准 |
| 4 | 0.44 s | 838 KB/s | ≈ 9× |
| **8（默认）** | **0.29 s** | **2550 KB/s** | **≈ 13.7×** |

每个小文件都要跑 `precreate → 分片 → create` 三次 HTTPS 往返，串行时绝大部分时间在等网络回包——所以并发是唯一有效的提速手段。8 并发已基本打满 20Mbps 上行，再往上收益递减；日志里若频繁出现 `errno=31034 命中频控`，把 `workers` 降到 4。

## 五、"手动确认"是怎么工作的

默认 `after_upload: "ask"`：所有批次传完后，终端列出成功清单，问你：

```
如何处理这些本地文件？
  m = 移动到已完成目录 (done_dir)
  t = 放入回收站（可找回）
  k = 保留在原处不动
请选择 [m/t/k]:
```

- 选 **m**：移动到 `done_dir`，重名文件自动加 `(1)`、`(2)` 后缀，绝不覆盖；
- 选 **t**：用 `send2trash` 送入 **Windows 回收站**，后悔了还能还原；
- 选 **k**：什么都不动。

想全自动就把 `after_upload` 改成 `move` 或 `trash`。

### ⚠ 已知坑：`C:\ProgramData` 下回收站会「报错但已删除」

Windows 的 `SHFileOperationW`（send2trash 底层用的就是这个）在 `C:\ProgramData` 这类
**系统/隐藏属性目录**下有个已知误报：文件**确实已被删除并进了回收站（可还原）**，
API 却返回 `ERROR_FILE_NOT_FOUND (2)`，于是日志里刷一片：

```
[错误] 处理 C:\ProgramData\...\xxx.txt 失败: [WinError 2] 系统找不到指定的文件。
```

实测（2026-09-22）：该目录下 20 个文件 **20/20 全部删除成功**，回收站元数据里能查到
原始路径（可还原），但 **20/20 全部抛异常**；换成临时目录则 0 报错。

现在的处理方式（`handle_uploaded`）：**以磁盘事实为准**——

- 抛异常但文件确实没了 → 记为成功，最多提示前 5 条 `[回收站·接口误报]`，不刷屏；
- 抛异常且文件还在 → 自动**回退成移动到 `done_dir`**，绝不静默丢下；
- 文件本来就不在（上一轮处理过）→ 直接跳过，不算失败；
- 结束时给一行汇总：`[上传后处理] 已送回收站 N 个（其中 M 个接口误报），失败 K 个`。

## 六、可靠性设计

- **断点续传**：每成功一个文件立刻写入 `uploaded_log.json`，中途中断（Ctrl+C / 断网 / 蓝屏 😉）后重跑自动跳过已成功的；
- **秒传**：网盘已有相同内容（MD5 分片一致）时直接秒完成，不耗流量；
- **分片重试**：4MB 分片上传失败自动重试 3 次（指数退避）；
- **失败重跑**：失败的文件下次运行自动重试；
- **Token 自动刷新**：过期自动用 refresh_token 续期；
- **进度文件写不进去也绝不中断上传**：`progress.json` 只是给面板看的，但 Windows 上
  它有个阴险的坑——只要**任何**进程此刻开着它的句柄（面板在轮询、杀软在实时扫描、
  资源管理器在做预览），`os.replace` 就会报 `WinError 5 拒绝访问`。实测：持有句柄
  20ms 时约一半的替换失败；8 个进程同时轮询也会稳定撞上；**让读方改用 `FILE_SHARE_DELETE`
  打开并不能避免（实测 16/16 仍失败）**，所以出路在写方：
  ① 重试 10 次（10ms 起线性退避，累计约 0.55s）；② 全失败就退回原地写（进度条这种
  场景容忍偶发的半截内容，总好过永久冻住）；③ 连原地写都不行就跳过本次更新，
  **只提示一次**，上传照跑。历史上这里没兜住，异常从线程池冒到主线程，整次上传当场
  结束（几千个文件白传过一回）；
- **进度落盘节流**：`PROGRESS_MIN_INTERVAL = 0.2s`，几千个文件不会每个都写盘
  （实测 60 个文件只落盘 8 次），顺带把撞上「句柄被占用」的概率降两个数量级。
  批次收尾、开始、结束这三处强制落盘，面板不会因此变迟钝；
- **面板不会把进度闪成 0**：读 `progress.json` 解析失败时重读一次，还不行就沿用
  上一次的好值（否则界面会闪一下归零，看着像任务被重置）；
- **开新任务先清旧进度**：点「开始上传」立刻把 `progress.json` 重置成空。上传进程要先
  扫完本地目录才写第一版进度，这中间（1.7 万个文件要扫一阵）若留着上一轮的
  `4782/4782`，界面会显示成「新任务已经跑完」；
- **本地扫描不再静默漏掉长路径文件**：路径超过 260 字符（Windows 的 `MAX_PATH`）时，
  Win32 API 直接报 `ERROR_PATH_NOT_FOUND (3)`，而 `Path.is_file() / exists()` 会把这个
  异常吞掉、返回 `False` —— 文件在**扫描阶段**就被当成「这不是个文件」跳过：不报错、
  不进统计、界面上一点痕迹都没有。实测某目录磁盘上实有 1142 个文件，工具只看到 1135 个，
  剩下 7 个（路径 264~286 字符）**从来没被上传过**，而界面一直说「扫描到的文件此前全都
  上传成功过了」。现在遍历与类型判定都走 `winpath.py`：`os.scandir(\\?\ 前缀)` 自己走目录树
  （`os.walk`/`rglob` 进超长子目录时会整棵静默跳过）、`stat_any` 取大小、`open_any` 读内容。
  另外**读不了的条目会单独列出来**并计数，宁可报出来让你看一眼，也不静默吞掉。
- **上传进程锁判活：`OpenProcess` 成功 ≠ 进程还活着**。Windows 上只要还有句柄
  指向进程对象（最典型的就是父进程里没释放的 `subprocess.Popen`），子进程退出后
  `OpenProcess` 照样能开出句柄。实测同一个刚 `wait()` 返回的子进程：
  `OpenProcess -> OK`，而 `GetExitCodeProcess -> 0`（真活着时是 `259 STILL_ACTIVE`）。
  旧实现只看 `OpenProcess`，于是上传**跑完或被强杀之后**，面板因为自己还攥着
  Popen 句柄，会一直认为上传在跑、拒绝启动新上传——只能重启面板才解得开。
  现在判活统一走 `proclock.py`（`OpenProcess` + `GetExitCodeProcess` 双检），
  面板、上传主程序、`organize_all.py` 三处共用同一份实现。`upload.pid` 是靠
  `atexit` 删除的，被强杀（蓝屏 / 关机 / 任务管理器结束进程）时会残留——
  残留本身无害，只要判活可靠，「残留」和「真在跑」就分得清。

## 六·五、本地还有没有没传的文件？（重新扫描上传）

断点记录（`uploaded_log.txt`）说「都传完了」，不等于本地一个不剩。想看准数字，
就用**忽略断点记录**的方式再扫一遍。

**网页面板**（推荐）：上传卡片里勾上「忽略断点记录」，然后

- 点「干跑预览」→ 结果里的**待上传**数字就是本地还没传过的文件数（这一步不上传任何东西）；
- 点「重新扫描上传」→ 勾选框会自动勾上，本地扫到的文件全部重新纳入上传。
  网盘里已有相同内容的会走**秒传**（按 MD5 分片判定），基本不耗流量、也不会重复占空间。

**命令行**：

```bat
python upload_baidu.py --dry-run --no-resume     :: 只核对，不上传
python upload_baidu.py --no-resume               :: 重新扫描并全部上传
```

什么时候用：① 怀疑断点记录与实际不符；② 移动过/换过本地目录；③ 想确认「本地真的
传干净了」再动手删本地文件。

> 平时不必勾它：默认的断点续传本身是可靠的（只有**真的上传成功**的文件才会写进记录）。
> `--no-resume` 是**核对与兜底**手段，不是日常用法。

## 七、常见错误码

| errno | 含义 | 处理 |
|---|---|---|
| -6 / 111 | Token 无效/过期 | 重新 `--login`（自动刷新失败时）；**整理归档**场景下这两个码（含 -9）常是**假失败**——整批共用一个错码而操作其实已生效，工具会自动核对纠正，见第十章的说明 |
| -9 | 文件不存在 | 单条一般是路径已变（文件被移动/改过名）；整批 100 条同时报，多半是假失败 |
| 31034 | 命中频控 | 把 `workers` 降到 4，并调大 `batch_pause_sec` / `file_interval_sec` |
| 31061 | 网盘已有同名同内容文件 | 无害，已按覆盖策略处理 |
| 31064 | 文件违规被拒 | 换文件或改文件名 |

## 八·五、上传完怎么确认没漏、没坏（verify_remote.py）

传了几万个文件，最后该删本地还是不敢删？跑一下核对：

```bat
python verify_remote.py                          :: 核对整个上传目录
python verify_remote.py --remote /apps/baidu_uploader/子目录名
python verify_remote.py --sample 50              :: 差异样本多显示点
```

它做三件事：**递归列出网盘真实文件** → **读本地 `uploaded_log.txt`** → **按相对路径双向比对**，最后给出：

```
网盘实际文件数   :           101
本地成功记录数   :           101
两边一致         :           101
网盘缺失(需补传) :             0
网盘多出(未记录) :             0
✔ 大小抽查：101 个本地仍存在的文件大小全部一致。
```

- **网盘缺失**：本地记录说传成功了、网盘里却没有 → 真正需要补传的。想补传就把对应行从 `uploaded_log.txt` 删掉再跑上传
- **网盘多出**：网盘有、本地没记录 → 多半是往轮次遗留，或源文件已被你删掉
- **大小不一致**：传了一半损坏的会被揪出来（只比对本地仍在的文件）

只读工具，不碰网盘也不碰本地文件。实测一个 101 文件的子目录耗时 2 秒、3 次接口调用；全量 3~8 万文件约几十秒。

> **它查不出的那一种漏**：`verify_remote.py` 是拿「本地记录」对「网盘实况」，所以只能
> 发现「记录说传了、网盘其实没有」。要是某个文件**压根没进过记录**（例如旧版本在长路径上
> 静默漏掉的），它两边都没有，自然对不出来。想连这一类一起查，用
> `python upload_baidu.py --dry-run --no-resume`，看输出的**待上传**数字 —— 那才是
> 「本地还有多少文件从没上传过」的直接答案（详见「六·五」）。

## 九、海量小文件实测备注（本次 9.9 万个文件调优经验）

- **`return_type` 语义**：precreate 返回 `return_type=2` 才是秒传；`return_type=1` 表示需要按顶层 `block_list` 指定的分片序号真实上传（实测确认，2026-09-20）
- **目录创建缓存**：同一远程目录只请求一次 mkdir，9.9 万文件不会重复建目录
- **断点记录**：`uploaded_log.txt` 追加写（一行一个路径），海量文件下不会越写越慢
- **频控退避**：遇 errno=31034 自动退避 30s/60s 重试
- **推荐参数**（海量小文件）：`batch_size: 500, workers: 8, batch_pause_sec: 5, file_interval_sec: 0`
- **单线程 vs 并发**：串行约 8 天（9.9 万文件），8 并发实测降到 5~7 小时
- **长时间任务**：双击 `start_upload.bat` 开跑，关闭窗口即暂停，再次双击断点续传；蓝屏/断网/重启都不丢进度

## 十、网页控制面板（推荐入口）

**双击 `open_panel.bat`**，浏览器自动打开 `http://127.0.0.1:8765/` 控制面板，可视化完成：

面板分四块：**① 参数设置与账号授权** / **② 上传控制** / **③ 实时进度** / **④ 网盘整理（批量改名 · 批量删除 · AI 计划）**。

- **参数设置**：AppKey/SecretKey、本地目录、网盘目录、并发路数、每批数量、批间暂停、文件间隔、大小上限
- **上传范围**：仅当前目录文件 / 含所有子目录
- **上传成功后处理**：保留原处 / 移动到指定目录 / 送入回收站（三选一）
- **账号授权**（就在参数设置卡片里）：一键打开授权页 → 粘贴授权码 → 验证登录；也可「复制网址」手动打开
- **上传控制**：干跑预览、开始（可设试传数量）、停止
- **上传前先改名**（可选，默认「不改名」）：选「只保留书名」或「去广告清理」，上传前先把本地文件改成干净名字
  - 改的是**本地磁盘上的真文件**，传上去自然就是干净名字；扫描口径与上传完全一致（同一套排除规则，同样跳过空文件和超上限文件），预览说改 N 个、实际就改 N 个
  - **绝不覆盖**：目标名已存在就跳过并记原因；只改大小写（`A.txt → a.txt`）是同名文件，正常放行
  - 每次改名都写一份记录到 `local_rename_log.jsonl`，点「回退上一次改名」可**整批还原**（原名被占用或文件已移走的会跳过，不会覆盖）
  - 点「开始上传」时会弹出改名清单再确认一次；上传进行中禁止改名（会让上传脚本对不上已传记录）
  - 默认不改名，是因为「只保留书名」会清掉 `Movie (2019).mkv` 里的年份——非小说目录会误伤
- **实时进度**：进度条 + 成功/失败统计 + 当前文件 + 滚动日志（每 2.5 秒刷新）
- **网盘整理**（详见下一节）：批量改名、整理归档、批量删除、AI 计划

### 网盘整理（卡片 4，只操作应用沙盒目录）

百度开放平台限制：接口只能操作 `/apps/baidu_uploader` 沙盒目录，整理功能在此范围内使用，越界请求会被后端直接拦截。

- **浏览**：列目录 / 上一级，回车即跳转；预览区显示子目录与文件
- **批量改名**，六种模式：
  | 模式 | 说明 |
  |---|---|
  | 查找替换 | 文件名里的某串替换成另一串（大小写不敏感） |
  | 加前后缀 | 统一加前缀/后缀，扩展名不动 |
  | 序号重命名 | 按顺序编号，模板 `{n}`=序号、`{name}`=原文件名 |
  | 正则替换 | 正则作用于不含扩展名的文件名，支持 `\1` 捕获组 |
  | 去广告/括号清理 | 自动去掉网址、广告词、多余括号和空格 |
  | 只保留书名 | 从小说名里提取书名，清掉作者、网站、尾部标注（详见下方） |
- **只保留书名**（整理小说用）：按**信号强度级联**，命中即停，五种信号都没命中就原样保留——宁可不动，也不乱改。
  1. 完整书名号 `《…》` → 取括号内。要求内容里不含书名号，所以 `《《一光年之恋》》` 这种错套会自动取到内层
  2. 残缺书名号 → 取最靠左的符号，右残取它前面、左残取它后面。`暗香情撩》by：季安` / `单飞雪《情难自禁`
  3. 作者标记（`作者：` / `著者` / `BY：`）→ 取标记之前。`by` 必须卡词边界，否则 `Baby`、`Hobby` 会被啃掉半截；且要求后面跟冒号或中文字，免得英文书名里的 `Stand by Me` 被切成 `Stand`
  4. 前导标签 `[悬疑]` / `【类型】` → 去掉
  5. 「空格-空格」作者分隔 → 取前面：`边荒传说 - 黄易` / `Rework - Jason Fried`

  最后统一清尾部标注：`全本`/`完结`/`番外`/`TXT格式电子书`/卷次括号。括号标注是**整组丢**——只删关键词会把 `(全+二番外)` 掏成 `(全+二)`，比不删更难看。
  `大漠苍狼1（绝地勘探）` 这类真副标题会保留；清成空名字时返回原名，绝不产生无名文件。
  - 实测 6 万个真实文件名：18% 会被改名，82% 名字本来就干净、一个字节都不动
- **撞名自动编号**：只保留书名会把 `《A》作者：甲`、`A - 乙` 压成同一个 `A`。这种撞车会**自动加 `(2)(3)`**，预览里标出「撞名，已编号」，并在提示里报出条数——两条都留住，比丢掉一条强，也比悄悄改名强。网盘侧只做「本批内部」去重，撞到网盘已有文件仍按重名策略处理；本地改名把磁盘实况也算进占用表
- **整理归档**：按大类（视频/文档/图片…）、按后缀、按修改年月，移动到「归档目录/分类名/」；同名自动跳过绝不覆盖
- **批量删除**：按后缀 / 文件名关键词 / 正则 / 大小区间筛选；执行前强制二次确认
- **空文件夹**：清掉「整棵子目录树里一个文件都没有」的目录
  - 判定是**递归**的：目录里只有空目录、空目录嵌套空目录，都算空——所以这个功能必然递归扫描，页签内会锁定「含子目录」开关（不递归只能得出「这层没东西＝空」的错误结论）
  - 预览只列**最外层**的空目录：删掉它，嵌在里面的空目录跟着消失。不逐层列的原因是一来列表会啰嗦几倍，二是父目录一删、子目录再删必然报「文件不存在」的假失败，把真实失败也淹没掉
  - 当前正在浏览的这层目录本身不会被删（免得删掉你正站着的地方）
  - 「跳过名字含」默认 `_覆盖备份`，命中的目录**连同整棵子树**都不动；而且这个保护会向上传染——只装着一个空的 `_覆盖备份` 的父目录也不会被删（否则等于绕道把保护对象删了）
  - **列不开的目录一律当「非空」保护**（见下节）：里面有什么我们不知道，绝不能当空目录删掉；它的每一级祖先也因此不算空
  - **整棵树一个文件都没有时额外提醒**：实测碰到过「先建好分类骨架、书还没放进去」的空结构（108 个目录 / 0 个文件 → 68 条删除计划）。这种「纯目录骨架」删掉之后分类结构也就没了，所以提示里会明说，不只是一个数字
  - 实测：3 层嵌套空目录只提交 1 条删除即整条链消失；含文件的目录、受保护目录、所有文件均不受影响
- **AI 计划**：点「导出文件清单」→ 复制到 WorkBuddy 对话让 AI 生成操作 JSON → 粘回面板「解析并预览」→ 执行。解析时逐条校验：路径必须在清单里、必须在沙盒内，越界或格式错的操作会被拦截并显示原因

#### 扫描遇到「打不开的目录」（百度侧的脏条目）

百度网盘会返回这样的条目：**父目录的列表里有它**（`isdir=1`），**拿它自己的 path 去列却回 `errno=-9`**。实测样本（名称已脱敏）：

```
/apps/baidu_uploader/<分类>/<子类>/<书名> <作者>　
```

同层 69 个目录里就这一个这样（名字尾部带一个全角空格 `U+3000`，全层孤例）；trim 尾部空白、
全角空格换半角、去掉全角空格**全都无效**；换 `order=name` / 不带 order / 换 `limit` / 换老接口
`/api/list` 也都是 0 条或同一个 -9——所以不是参数问题，是百度侧那份索引对不上，客户端无解。
（那个目录本身确实是空的：`search` 接口能搜到它，`size=0`。）

以前的行为是「一遇到就抛异常」，于是**几千个目录的大扫描被这一个条目全废掉**，它跟其余 99.9% 的目录毫无关系。现在的处理：

- **不让它毁掉整次扫描**：子目录列不开就记下来跳过，继续扫别的。起点目录列不开仍然当场报错（说明路径或沙盒配置本身有问题，必须让你看见）
- **结果如实标注不完整**：提示里报出「⚠ N 个目录打不开，里面的文件没扫到（结果不完整）」，并点名具体是哪几个。悄悄少扫一个目录比直接报错更危险——你会以为「就这些文件」，然后照着这份「完整」清单去改名/删除
- **空文件夹页签**额外说明「无法确认里面是否为空（已排除、不会删）」，措辞**不会**说「很干净」
- **导出给 AI 的清单**开头也会带一行注释，说明有目录没扫进去，免得 AI 把「清单里没有」当成「网盘里没有」
- 授权失效 / 被限流（`-6` / `111` / `31034`）属于全局性错误，**不跳过**，直接报错——那种情况下每个目录都会失败，静默跳过只会给出一份假结果
- 报错文案也翻成了人话：`列目录失败（目录不存在，可能已被移动或改名）：/apps/…`，不再甩原始 JSON

#### 预览文件（本地存盘，不再每次重扫网盘）

改名 / 归档 / 删除的预览都必须先把网盘**递归扫一遍**。沙盒里几万个文件时一次要好几分钟，
而实际用起来常常是「看一眼 → 改个参数 → 再看一眼」，每次都重扫纯属白等。所以每次生成预览
都会**落盘成一份预览文件**，并在里面记一份**指纹**——影响结果的全部输入（类型 / 目录 /
是否递归 / 模式 / 参数 / 沙盒 / 筛选条件）的 sha1。

- **生成预览**：先按指纹找同参数的旧预览，命中就直接拿来用，**一个网盘请求都不发**；没命中才真扫，扫完存一份到 `previews/`
- **重新生成**：跳过复用，强制重扫一遍（参数没变但网盘变了时用它）
- **预览文件下拉**：列出所有存下来的预览（时间 · 类型/模式 · 条数 · 扫描范围），挑一份**载入即可直接执行**，不必重新扫描
- **删除这份 / 清理已执行**：管理本地的预览文件；最多留 50 份，超了自动丢最旧的

两条硬规则：

1. **参数变一个字就重扫**——指纹覆盖了所有影响结果的输入，绝不会把「按大类」的旧预览当成「按后缀」的结果给你
2. **执行过的预览不再复用**——执行完网盘已经不是当时的样子了，那份清单里可能一半路径都已不存在。所以宁可让人重扫一次。列表里会把它标成「已执行〔时间〕」；万一还是载入了它去执行，二次确认会额外警告「这份预览已经执行过一次」

另外：载入的预览在执行前会**重新做一遍越界校验**（预览文件就是磁盘上的普通 JSON，能被手改，也可能是换了 `remote_dir` 之前生成的）；执行超过 10 分钟的旧预览时，确认框会额外提醒网盘可能已变。

安全设计：所有操作**先预览后执行**（预览列表只回传前 2000 条，执行时按完整计划 2000 条一批跑完）；删除类操作必须二次确认；移动/改名遇同名自动跳过。

### ⚠ 报「失败 1800 条」但文件其实都搬好了 —— 百度的整批假失败

2026-09-23 实测：一次 2000 条的「整理归档」，界面报「移动 200 / 失败 1800」，
明细里 500 条 `-9 文件不存在`、1300 条 `111 Token 过期`。可实地核对下来——
源目录里那 2000 个文件**一个不剩**，全都到了 `/归档/txt`。

原因：`filemanager` 在高并发、大批量提交时会**整批回一个错误码而 `info` 为空**，
而操作其实已经入队执行了。当时的诱因是**上传任务正在同时运行**（同账号同 token
一起猛敲百度）。失败分布也很说明问题——整批 100 条共用一个错码，逐批在 `-9` 和
`111` 之间随机跳，而不是「这些文件真的不存在」那种逐条差异。

#### 更狠的一次：报错是 info **逐条**给的，一条都没被核对

2026-09-24 又来一回，而且更隐蔽：2000 条报「移动 388 / 失败 1612」，
明细里 1300 条 `-9`、200 条 `111`、100 条 `31033`、12 条 `-8`。
事后把 1612 条全查了一遍，结果是：

| 报错码 | 条数 | 实地核对的结果 |
|---|---|---|
| -9 文件不存在 | 1300 | **1267 条早就搬走了**，33 条原处还在 |
| 111 Token 过期 | 200 | 99 条已搬走，92 条真没动 |
| 31033 | 100 | 98 条真没动（限流那一批） |
| -8 撞名 | 12 | 12 条全是目标处已有同名 |

也就是说 **1612 条里有 1366 条（85%）其实是成功的**，界面却全报成失败。
为什么没被核对纠正？因为那次的错码是 `info` 里**逐条**给的，而早先的复核只认
「整批报错且 `info` 为空」这一种形态 —— 这 1612 条一条存疑标记都没有，压根没进复核。

现在的处理（`pan_tools.py`）：

1. **凡是能用磁盘事实证伪的错误码，一律先记「存疑」，事后核对**——不光整批报错，
   `info` 里逐条给的 `-9 / -8 / -7 / 12 / 111 / 31033 / 31034 / 31061 / 31066` 一样算。
   判据仍是「原处已无 **且** 目标处已有」，但**核两遍**（间隔 4 秒）：百度目录索引
   有延迟，刚搬完立刻 list，源处可能还挂着旧名字，只核一遍会把成功误判成失败
2. **仍失败的自动重试一轮**：限流、整批被打回这类「这一趟没赶上」的，再提交一次
   通常就成了。撞名和「文件压根不在」重试也没用，不做无用功
3. **失败原因说到点子上**：`原处还在，目标处已有同名文件（撞名未覆盖）`、
   `原处还在，没生效`、`原处和目标处都没有它`、`目录读不到，无从核对` ——
   不再是一句含糊的「复核 N 次均未生效」
4. **连接级错误码（-6 / 111 / 31034）先探一次连接**：真断了就立刻停，剩下的如实标
   「未执行」并说明原因——不再把后面十几批白白提交一遍，也不给它们编造错误码
5. **执行时上传任务在跑会给出提示**：两者同时操作网盘正是本次假失败的诱因

结果文案会长这样：`完成：移动 1754，失败 246；其中 1366 条百度返回了错误码，
已按网盘实际内容核对确认生效；另有 98 条第一次没生效，自动重试后完成`。

面板执行时会把计划按 **2000 条一批**提交给百度（它一次吃不下太多），但**总条数
没有上限** —— 扫出来多少就跑多少，点一次「执行」即可（见下一节）。嫌面板不方便
也可以用 `organize_all.py`，它自动循环到搬完：

```bat
:: 先干跑看清计划（不上传、不移动，只扫描统计）
python -X utf8 organize_all.py --path "/apps/baidu_uploader/某某小说合集" ^
       --by ext --dest /apps/baidu_uploader/归档 --dry-run

:: 确认无误后去掉 --dry-run 真跑；上传任务在跑时它默认拒绝执行（--force 可强行）
```

`--by` 可选 `ext`（按后缀）/ `category`（按大类）/ `date`（按修改月份）；
`--ondup overwrite` 则撞名时先把旧文件挪进 `_覆盖备份/时间戳/` 再覆盖。

### 十万条计划怎么一次跑完

整理整个沙盒能扫出 **105370 条**。直接点「执行」就是全部跑完：生成预览时会把
**完整**计划另存一份到 `plans/<预览id>.json`（界面列表里只回传前 2000 条，十万条
全传回去要几十 MB，也翻不完），执行时后端照着这份清单按 **2000 条一批**连续提交，
不必每轮重新扫描网盘 —— 源路径不会变，清单本身是准的。

- 进度条显示「第 N/M 批」，右边有「停止」按钮：跑完当前这批就停，**已执行的部分
  照常生效**，剩下的不会动（重新生成一次预览就能接着跑）。
- 完整计划一份能有几 MB，只保留最近 5 份；删预览文件时它跟着一起删。
- 旧版本生成的预览没有这份完整计划，执行时只能跑列表里那 2000 条 —— 界面会在
  执行按钮的提示和确认框里说明，结果文案也会写「共 N 条、本次只跑了这些」。
- ⚠ 一次动十万条是不可逆的大动作，点执行前先确认目标目录是不是你想要的
  （尤其是「目标在被整理目录之内」这种自搬自的配置）。

### 撞名：十万个文件塞进 /txt 必然撞，现在自动编号

把整盘按后缀拍平，重名是躲不开的（实测 2000 条里就撞了 56 条）。撞上以后：
跳过策略下这些文件**永远搬不完**，每轮都报一批失败；覆盖策略下旧文件被挤进
`_覆盖备份/`，同名越多备份区越膨胀。

生成计划时现在做两件事：

1. **已经在目标目录里的文件不再生成操作**（`/txt` 里那 3933 个上次搬好的不再折腾
   ——硬搬一次等于在自己目录里撞自己的名）
2. **目标目录已有同名的，给后来的自动加 `(2)(3)…`**，编号插在后缀前面
   （`《A》甲.txt` → `《A》甲 (2).txt`）。2026-09-28 起撞名的用 **move 带 newname
   一步到位**（实测百度 filemanager move 支持 newname）——不再拆「改名+移动」
   两条：两条不但慢一倍，改名那步失败还会让后面移动撞出 -8，十万条量级下
   这种连锁失败是灾难（上一版 27168 条改名里失败了 25901 条）

新名字还要避开**源目录**里已有的同名（否则改名那一步就在原地撞车），
两边都放得下才用。

### 合并重复目录：打破「整理不完」的死循环

2026-09-28 发现归档下 ~40% 是 `(1)` 副本目录（mobi(1) 40957 个文件、pdf(1)
15861 个……），txt 与 txt(1) 之间有 **7710 对同名文件**。后果是「按后缀整理」
永远收不了尾：一对同名文件在扫描里就是两条计划，每轮扫出来的计划都比真实
文件多——这就是「生成的预览文件总是比真实文件数量多」的根因。

「网盘整理」卡片新增**「合并重复」页签**：

- 同一位父目录下同时有 `X` 和 `X(1)`（`X(2)`…`X(9)` 也归到 X）就算一对，
  副本里的文件搬回主目录，撞名的自动编号
- 两条安全红线：副本里的**子目录**不动；搬空的副本**不在同一份计划里删**
  （百度 delete 对目录是连根拔的，万一有文件没搬成，删目录就是销毁真数据）。
  搬完用「空文件夹」页签清理，那边按扫描实况判空
- 括号里是两位以上数字的不算重复（`报告(2024)` 是正经名字，不是 `报告` 的副本）

顺带修了垃圾目录：怪文件名拆出来的「后缀」直接当目录名，攒出过 `com)]`
（1088 个文件）、`pdf（滚雪球英文原版——巴菲特的传记）`、`李华东&amp` 这种
目录。现在后缀派生的目录名会清洗：首字符不是 ASCII 字母数字的归 `noext`，
其余只留字母数字。

### 扫描提速：4 线程并发列目录

生成预览慢的主因是几千个目录**串行**列（2T 网盘要好几分钟）。列目录是纯只读，
现在默认 4 线程并发（`LIST_WORKERS`），实测 60 目录 × 20ms 延迟的场景从 1.28s
降到 0.34s。容错（坏目录记 failures）、停止、致命错误上抛这些行为与串行版
完全一致（`_t_conc_scan.py` 专项盯住）。

说明：
- **改动自动保存**：表单任意字段改完停手 0.8 秒即自动写入 `config.json`，按钮旁显示「✓ 已自动保存 时:分」；必填项没填齐时不会写入，并提示还差几项
- **授权只需一次**：Token 存在本地 `token.json`（默认有效期 30 天，到期自动续期），头部徽章显示「已授权（有效期至 YYYY-MM-DD）」，刷新页面、重启工具都不用重新授权
- 面板只监听本机 127.0.0.1，外部无法访问
- **关闭面板/页面不影响正在进行的上传**，上传是独立后台进程
- 面板临时实例（如由 AI 会话代起的）超时会退出，日常用 `open_panel.bat` 自己起即可
- 不想用面板的话，命令行方式照旧：`start_upload.bat` 或 `python upload_baidu.py`

## 十三、一键推送到三个远程仓库（push-all.bat）

本项目同时托管在三个平台，双击 `push-all.bat` 一次推完：

| 平台 | 地址 | 协议 |
|---|---|---|
| GitHub | https://github.com/SimianLee/baidu-uploader.git | HTTPS |
| GitCode | git@gitcode.com:SimianLee/baidu-uploader.git | **SSH** |
| Gitee | https://gitee.com/SimianLee/baidu-uploader.git | HTTPS |

> GitCode 之所以单独走 SSH：该平台已移除密码认证，HTTPS 推送必失败（见下）。

### 用法

| 命令 | 作用 |
|---|---|
| `push-all.bat` | 推送当前分支到三个库（首次运行会自动做初始化提交） |
| `push-all.bat setup` | 只配置三个远程地址，不推送 |
| `push-all.bat ssh` | 改用 SSH 地址推送（HTTPS 不通时用） |
| `push-all.bat commit "说明"` | 先 `git add -A` + commit 再推送 |

### 它做了什么

1. **推送前安全自检**：若 `config.json` / `token.json` / `libs/` / `uploaded_log.txt` 已被 git 跟踪，立即中止并给出 `git rm --cached` 的解法——防止密钥泄漏到公开仓库
2. **幂等配置远程**：三个远程不存在就添加、地址不对就纠正，重复运行无副作用
3. **失败自动回退 SSH**：某库 HTTPS 推送失败后，自动换 SSH 地址再试一次（github 的 443 常被代理挡成 502，gitcode 只能走 SSH，靠这一步实现双击一次全通）
4. **依次推送并汇总**：每个库的原始输出实时显示，结束给出成功/失败统计
5. **写日志**：`push-logs/push-<时间戳>.log`（完整）+ `push-logs/history.log`（历次一行摘要，UTF-8 带 BOM，记事本打开不乱码）

### GitCode 为什么要走 SSH（2026-09-20 实测）

HTTPS 推送会直接失败：

```
remote: <CH.00905401> HTTP Basic: Access denied.
remote: The password-based authentication of Git has been removed.
        Please use your personal access token instead of the password.
fatal: Authentication failed for 'https://gitcode.com/...'
```

原因不是账号密码输错，而是 **GitCode 已经彻底移除密码认证**，HTTPS 只剩两条路（私人令牌 / SSH）。脚本默认选了 SSH，因此双击即可一次推完三个库。

若哪天报 `Permission denied (publickey)`，说明 `~/.ssh/id_rsa.pub` 的公钥没加到 GitCode 账号，去「个人设置 → SSH 公钥」粘贴一次即可（本机密钥已存在：id_rsa / id_rsa.pub）。

> 脚本可重复运行：已推送成功的库会显示 `Everything up-to-date` 直接跳过，只补推落后的那个。
